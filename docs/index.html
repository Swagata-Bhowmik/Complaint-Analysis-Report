👋 The whole idea in 30 seconds

A bank gets thousands of complaint letters a week — double charges, fraud, app crashes, rude service. No human can read them all, so the single most valuable piece of information — what is actually going wrong — stays buried, and managers guess. This project builds a machine that reads every complaint, groups the similar ones into themes, scores how serious each is, and returns a ranked list: "here are the top problems, fix these first." Nobody labelled the themes — it discovered them on its own.

🎯 Chapter 1 — The Problem & The Goal

Before any code: what business pain are we solving, and how will we know we won?

This chapter owns: the business case — the "why" behind the whole project
😖 The pain, concretely
A bank receives thousands of complaints every week in free-form English — a double charge, a fraudulent transaction, an app that failed, a rude agent. Reading them one-by-one is impossible, so the richest signal a company owns — its customers telling it exactly what is broken — is wasted. Teams react to whoever complains loudest, not to what is most common and most damaging.
🎯 The three questions we must answer
1. What are people complaining about? → discover the recurring themes.
2. Which problems matter most? → rank by how common AND how severe.
3. So what do we fix first? → a clear ordered "fix-first" list + a reusable tool.
💼 Why this is worth money
Turning raw text into a ranked action plan means the company fixes the right things first — reducing refunds, chargebacks, churn and call-centre load, and protecting trust. It's the difference between "we ran an algorithm" and "we answered a business question that saves money."
Interview one-liner: "I built a system that turns raw customer complaints into a prioritized action plan — the top problems ranked by frequency and severity, delivered as a dashboard and a self-serve upload tool."

📚 What the data is
The CFPB Consumer Complaint Database — published free by the U.S. Consumer Financial Protection Bureau (a government body). The field that matters is the narrative: the customer's own written story. That free text is the raw material the whole engine runs on.
🧭 Why THIS data — and deliberately not scraping app reviews
A compliance decision: government open data is explicitly free to use, while scraping the Play Store / App Store violates their terms of service, can get you blocked, and pulls in personal data (privacy risk). "Publicly visible" is not the same as "free and safe to bulk-collect." CFPB is also large, real, and problem-focused (complaints, not star ratings).
💡 EDA (Exploratory Data Analysis) — looking hard at your data before building anything — how big, what's inside, what's missing, what's weird — so you don't draw wrong conclusions. Skipping it is how analysts quietly build on sand.
💡 Chunked / out-of-core processing — the file is 8.5 GB, too big for memory, so we read it in chunks of 200,000 rows, summarised each, and discarded it before the next. Like drinking a lake through a straw instead of swallowing it whole.
🔬 What profiling the full file told us
• 17.1M complaints; only 3.8M (22%) have narratives (opt-in).
• Narratives only exist from 2015 onward, so the oldest rows look empty — judging from the first chunk gave a misleading "0.7% have text" because the file is oldest-first.
• Volume is exploding: 2025 alone had ~1.2M narratives.
• Product labels are messy — the same product appears under multiple names ("Credit card" vs "Credit card or prepaid card"); they must be merged or you double-count.
🎯 How we narrowed 17M down to our working set
Scope: Product = Credit card (both variants merged), only rows with a narrative, and 2023 onward. Filtering in chunks produced 124,962 credit-card complaints — the slice we then cleaned.

🧹 Chapter 3 — Cleaning the Text

Careful, evidence-first cleaning that removes noise without destroying meaning.

This chapter owns: how raw messy text became model-ready — and why every choice was conservative
Before cleaning

Removed

🔎 We measured the mess before touching it
• 12,268 exact-duplicate narratives (~10%).
• 75.9% contain XXXX privacy masks (median 4 each).
• 42.5% contain money masks like {$70.00}; many contain XX/XX/year> dates.
• 256 narratives shorter than 50 characters (too little signal).
🧯 Why each is a problem
Duplicates lie about how common a problem is; privacy masks are pure noise to a meaning model; two labels split one theme into two; ultra-short texts carry almost no meaning.
💡 Regex (regular expressions) — a tiny pattern-matching language for find-and-replace in text. Example: X{2,} means "two or more capital X's in a row" — that's how we detect a redaction like XXXX and swap it out.
🧼 What we did — carefully, not aggressively
Removed exact duplicates; merged the two product labels; turned privacy masks into neutral placeholders (<redacted>, <date>, <money>) instead of deleting them; dropped <50-char texts; and kept the original text in its own column for before/after auditability.
💡 Why placeholders instead of deleting? Deleting every XXXX shatters sentences ("In my was charged"). A neutral placeholder keeps the sentence readable and its meaning intact while removing the identity noise. Over-cleaning destroys signal.
Before: "In XX/XX/year>, XXXX applied charges higher than I agreed…"
After: "In <date>, <redacted> applied charges higher than I agreed…"

🧠 Chapter 4 — The AI Engine

The teaching chapter. This is where a computer actually "reads" complaints and finds the problems. Every concept is explained from zero — read this one slowly.

This chapter owns: ALL the machine-learning concepts. Other chapters just refer back here.

The engine is a 5-step pipeline; each step feeds the next:

1 · Embeddings2 · Clustering 3 · TF-IDF keywords4 · Severity 5 · Priority+ LLM naming

🧠 Step 1 — Embeddings: give each complaint a location on a "meaning-map"

The core idea
Computers understand numbers, not words. So we turn each complaint into a list of 384 numbers called an embedding (or vector). The magic rule: complaints that mean similar things get similar numbers. "I was charged twice" and "I got double-billed" land right next to each other even though they share almost no words. Picture every complaint as a dot on a giant map where distance = difference in meaning.
💡 Embedding / vector — a fixed-length list of numbers that captures the meaning of text. Think of it as a GPS coordinate in "meaning-space": similar meaning → nearby coordinates.
💡 The model: all-MiniLM-L6-v2 — a small, free, pre-trained AI model that produces the 384-number vectors. We didn't train it; we used it. It runs on a normal laptop CPU. Embedding all 112k took ~75 minutes, so we ran it once and saved the vectors — every later step reloads them in a second.

🧩 Step 2 — Clustering: circle the crowds on the map

The core idea
Now every complaint is a dot on the map. Clustering finds the natural crowds of dots. Each crowd is a group of similar complaints = a theme. Nobody told the computer the themes — it discovered them. That's unsupervised learning (learning with no answer key).
💡 KMeans — you tell it "make K groups" (we chose K=12). It drops 12 flags on the map, assigns each dot to its nearest flag, moves each flag to the centre of its dots (the centroid), and repeats until the groups stop moving. The centroid is just the average position of a group.
💡 Why K = 12? Enough groups to separate genuinely different problems without splitting hairs. It's a starting choice you inspect and adjust — in the Streamlit upload tool you can slide K yourself and watch the themes change.

🔤 Step 3 — TF-IDF: find the words that make each theme distinctive

💡 TF-IDF (Term Frequency – Inverse Document Frequency) — a score that is high for words common inside one theme but rare everywhere else. "the" and "card" score low (they're everywhere); "chargeback" scores high if it clusters in one theme. We use the top-scoring words as each theme's keyword label. Shortcut: the words that make this group special.

⚠️ Step 4 — Severity: how bad is each problem, not just how common?

Why volume alone is not enough
A theme can be huge but mild (rewards confusion) or smaller but devastating (identity theft). A business cares about both, so we score how serious each complaint is using two honest signals combined.
💡 Signal 1 — VADER sentiment — sentiment analysis judges the emotional tone of text. VADER is a fast, dictionary-based tool giving a "compound" score from -1 (very negative) to +1 (very positive). We flip it onto a 0–1 scale where 1 = most negative. No GPU, no API, fully transparent.
💡 Signal 2 — high-stakes keywords — the share of complaints in a theme mentioning genuinely serious words (fraud, unauthorized, stolen, scam, identity, threat, legal, police, victim).
Combining them
theme severity = average of (negativity) and (high-stakes share), both 0–1. We're honest that this is a proxy for severity, not ground truth — VADER can misread sarcasm and the keyword list is hand-picked. Stating that is a strength.

🏆 Step 5 — Priority: the smart ranking

The formula
Priority = Volume (%) × Severity. This surfaces problems that are both common AND serious — not a popularity contest. It's the classic business priority matrix: volume on one axis, severity on the other; top-right (common + severe) = fix first. You can see that exact chart in Chapter 5.

🏷️ Final touch — an LLM gives each theme a human name

From "Theme 0" to "Unauthorized Charges & Fraud Disputes"
The groups start as bare numbers. We send each theme's top keywords + 3 real example complaints to an LLM and ask for a short name and description as strict JSON, so our code can read it. If a call fails, we fall back to the TF-IDF keyword label — the pipeline never breaks.
💡 LLM (Large Language Model) — here Google Gemini — an AI that understands and writes human language. We used the free tier via an API (our code talking to Google's AI). The secret API key lives in a hidden .env file, never uploaded to GitHub. Classic ML (embeddings + clustering) does the heavy lifting; the LLM just adds a readable label on top.
💡 PCA (Principal Component Analysis) — our vectors have 384 dimensions, impossible to draw. PCA squashes them to 2 while keeping the biggest patterns, so we can plot the meaning-map as a flat scatter. Used only for the picture.
The whole engine in one breath: embeddings turn text into meaning-vectors → KMeans clusters them into themes → TF-IDF labels each → VADER + keywords score severity → volume × severity ranks them → an LLM names them.

🎓 Chapter 7 — Discoveries & What I Learned

The honest engineering story — the bugs caught, the surprises, and the working habits.

This chapter owns: the real problems hit and the lessons
🐞 The bug we caught — silently corrupted dates
After extracting our slice, a "complaints per month" chart looked flat and wrong. Investigating showed only ~6,281 of 124,962 dates were valid — the rest were NaT (missing). Root cause: across an 8.5 GB CSV, pandas inferred the date column's type differently in different chunks, and joining them coerced most dates to missing. Fix: convert dates inside each chunk before joining, and switch from CSV to Parquet (176 MB → 74 MB). Result: 124,962/124,962 valid. Lesson: never trust a result that looks off; sanity-check it.
📈 The surprise — more data gave cleaner themes
On the 18k sample, "fraud" smeared across ~3 overlapping clusters. On the full 112k those sub-types separated into distinct categories. More data → centroids estimated from more points → less noise, more stable clusters.
🧪 The habit — validate everything
We built a reusable validate() function and ran it after every data step (size, nulls, duplicates, valid dates, sane labels). Validating after a transformation — not just before — is what caught the date bug.
🧯 The honesty — knowing the limits
Severity is a proxy (lexicon + hand-picked keywords), not ground truth. KMeans needs K up front and assumes round-ish clusters. Some themes still overlap. Stating these openly shows judgement.
🔑 The engineering call — separate the slow step
Embedding 112k takes ~75 min, so it's its own script that saves the vectors — an interruption in later analysis never wastes that expensive compute.

🧷 The GitHub workflow (stage → commit → push)

💡 Commit vs push — a commit is a save-point on your computer; a push uploads commits to GitHub. You commit many times locally and push once.
git add <files>            # stage the files to save
git commit -m "message"    # seal a save-point locally
git push                   # upload to GitHub

# first time only:
git init
git remote add origin https://github.com/<user>/<repo>.git
git branch -M main
git push -u origin main
Key discipline: the big data files, the .venv, and the secret .env are listed in .gitignore so they are never uploaded. Repos hold code, not gigabytes or secrets.

🌍 Deploy the dashboard (Streamlit Community Cloud, free)

The steps
1. Push the repo (app code, requirements.txt, deploy_data.json) to GitHub. 2. Go to share.streamlit.io and connect GitHub. 3. Pick the repo; set the app file project1_insight_engine/app/insight_app.py. 4. Streamlit installs requirements.txt and serves a public URL. 5. The hosted app reads the tiny deploy_data.json; the heavy data stays local and the secret key is never shipped.
⏰ Scheduled auto-refresh (planned)
Using GitHub Actions (free), the pipeline can run on a timer — pull newest complaints, re-run the engine, and refresh a "top new issues this week" report by itself. On-demand for humans, scheduled for the robot.
